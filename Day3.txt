## 🧠 1. The Big Picture: What are we building?

We are building an AI Agent that possesses domain-specific knowledge that the LLM was *not originally trained on*. 
Standard LLMs hallucinate when asked highly specific or private questions (like "What are the rules of my company's HR policy?"). 

To solve this securely and efficiently, we build a **RAG (Retrieval-Augmented Generation) Agent**.

**Definition:**
> **RAG = Retrieval (Fetching correct data) + Generation (LLM answering using that data).**

Instead of hoping the LLM "knows" the answer, we search for the specific document snippet first, give it to the LLM, and tell it: *"Answer the user's question using ONLY this provided document."*

---

## 🔄 2. The Complete RAG Workflow

The flow is highly structured and forms the backbone of modern Enterprise AI.

```mermaid
graph TD
    A[User Question] --> B[Convert Question to Embedding Array]
    B --> C[(Vector Database)]
    C -->|Semantic Search| D[Retrieve Top 3 Relevant Text Chunks]
    D --> E[Combine Chunks + Question into a Prompt]
    E --> F[Send to LLM]
    F --> G[Generate Final Grounded Answer]
```

## 🔢 3. Embeddings: The Core Mathematical Concept

**Definition:**
An **Embedding** is a numerical (vector) representation of text. 

**Why are they necessary?**
Computers cannot understand raw text or meaning. They only understand math. Embeddings translate sentences into high-dimensional arrays (lists of numbers). 

By converting text into vectors, we can map concepts spatially. Words or sentences with similar *meanings* will have vectors that point in roughly the same direction, allowing us to perform mathematical calculations to measure their similarity.

**Example:**
* `"The food is delicious"`  → `[0.21, -0.44, 0.78, ...]`
* `"This meal tastes great"` → `[0.22, -0.41, 0.75, ...]`

Even though there are zero overlapping words in those two sentences, their array numbers are mathematically very close. A traditional keyword search (like `SQL LIKE %food%`) would fail here, but an embedding search succeeds perfectly.

**Interview Point:**
> Embeddings capture deep semantic meaning, not just surface-level keywords.

## 🗄️ 4. Vector Databases

**Definition:**
A specialized database designed specifically to store dimensional embeddings and perform blazing-fast semantic similarity searches (like Cosine Similarity or Euclidean Distance).

**Why not use PostgreSQL or MongoDB?**
Traditional DBs index text by characters and keywords. Vector DBs index data by its position in mathematical space. 

**Popular Vector DBs:**
* **ChromaDB** / **Pinecone** / **Weaviate** / **Milvus** / **pgvector** (Postgres extension)

---

## ✂️ 5. Chunking: Document Splitting

**Definition:**
Breaking large documents (like a 100-page PDF) into smaller, bite-sized pieces (usually 300 to 1000 tokens) before embedding them.

**Why is chunking necessary?**
1. **LLM Context Limits:** You cannot pass a 500-page PDF entirely into an LLM window due to token limits and costs.
2. **Retrieval Precision:** If you embed an entire book as one vector, the vector becomes "noisy" and mixed. By embedding smaller chunks, you ensure that specific paragraphs match specifically to precise user questions.

**Common Chunking Strategies:**
* **Character splitting**: Splitting every 1000 characters.
* **Recursive text splitting**: Searching for natural paragraphs (`\n\n`) and sentences (`.`) so chunks don't cut off mid-thought.

## 🛠️ 6. LangGraph: The Next Evolution of LangChain

While `LangChain` is excellent for simple, linear pipelines (Prompt -> LLM -> Output), it becomes incredibly difficult to manage when you need complex loops, conditions, and human-in-the-loop workflows.

**LangGraph** solves this by modeling AI workflows as stateful, cyclic graphs (hence the name).

### 🆚 LangChain vs. LangGraph

| Feature | LangChain (`runnable` sequence) | LangGraph (`StateGraph`) |
| :--- | :--- | :--- |
| **Execution** | Linear (`A -> B -> C`) | Graph-based (can loop `A -> B -> A`) |
| **State Tracking** | Memory is manual and injected per chain | State is unified and managed automatically |
| **Resilience** | Difficult. Errors crash the chain. | Supports check-pointing, pause, and rewind. |
| **Best For** | Simple RAG, basic chatbots | Autonomous Agents, Multi-Agent routing |

## 💻 7. Practical Code: Creating a LangGraph Agent with Tools

Let's look at how we combine LLMs and Tools inside the LangGraph ecosystem using Node/TypeScript.

### Step 1: Initialize the Brain (LLM)
```javascript
import { ChatOpenAI } from "@langchain/openai";

// Core Brain
const llm = new ChatOpenAI({
  apiKey: process.env.OPENAI_API_KEY,
  modelName: 'gpt-4o',
  temperature: 0, // 0 prevents hallucination in critical tasks
});
```

### Step 2: Create a Tool
Tools in LangChain/LangGraph are tightly typed wrappers around standard functions.
```javascript
import { tool } from "@langchain/core/tools";
import { z } from "zod";

// A tool the agent can use to multiply numbers
const multiplyTool = tool(
  async ({ a, b }) => {
    return (a * b).toString();
  },
  {
    name: "multiply",
    description: "Multiply two numbers. Use this for math.",
    // Zod schema enforces the LLM passes an object with exactly 'a' and 'b' as numbers
    schema: z.object({
      a: z.number(),
      b: z.number(),
    }),
  }
);

// Bind the tool so the LLM is aware it exists
const llmWithTools = llm.bindTools([multiplyTool]);
```

### Step 3: Build the StateGraph
The `StateGraph` defines the flow. It holds a global `messages` array via `MessagesAnnotation`.
```javascript
import { StateGraph, MessagesAnnotation } from "@langchain/langgraph";
import { ToolNode } from "@langchain/langgraph/prebuilt";

// Node 1: Call the LLM
async function callModel(state) {
  // Pass the accumulated conversation history to the model
  const response = await llmWithTools.invoke(state.messages);
  return { messages: [response] }; // Reducer auto-appends this to global state
}

// Node 2: The Tool Execution Node (provided by LangGraph)
const toolNode = new ToolNode([multiplyTool]);

// Route Condition: Should we call a tool or end?
function shouldContinue(state) {
  const lastMessage = state.messages[state.messages.length - 1];
  if (lastMessage.tool_calls?.length) {
    return "tools"; // Proceed to ToolNode
  }
  return "__end__"; // End execution
}

// Compose the Graph
const workflow = new StateGraph(MessagesAnnotation)
  .addNode("agent", callModel)
  .addNode("tools", toolNode)
  .addEdge("__start__", "agent")
  .addConditionalEdges("agent", shouldContinue)
  .addEdge("tools", "agent"); // Loop back to agent after tool finishes

// Compile into a runnable app
const app = workflow.compile();
```

## 🎯 8. Core Interview Questions

### ❓ Q1: What is RAG and why is it preferred over Fine-tuning?
**A:** RAG stands for Retrieval-Augmented Generation. It gives the LLM context from a database *during* the prompt. Fine-tuning attempts to bake knowledge permanently inside the model's weights. RAG is cheaper, allows for real-time data updates (just update the database), and heavily reduces hallucination through factual grounding.

### ❓ Q2: What is the purpose of Embeddings?
**A:** Embeddings convert words and sentences into dense vectors (arrays of numbers) so that semantic similarity can be measured mathematically. This powers the semantic search capabilities of Vector Databases.

### ❓ Q3: Why is Chunking important in RAG pipelines?
**A:** Chucking manages token constraints and improves retrieval precision. Feeding a massive document into a vector DB creates a noisy embedding. Chunking ensures we match specific queries to hyper-specific paragraphs or sentences.

### ❓ Q4: What makes LangGraph a superior framework to LangChain for Agentic workflows?
**A:** Simple chains are linear. Real agents require cyclical logic, loops, routing based on observations, and state persistence over a long lifetime. LangGraph represents workflows as a Directed Graph, seamlessly managing loops, parallel execution, and shared state across nodes.
